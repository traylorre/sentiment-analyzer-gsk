# Feature 1398: cross-source-dedup-fix — LB-1: Cross-Source Dedup Merge Never Fires

**Status:** DRAFT (spec/plan/tasks only — NO implementation in this battleplan stage)
**Priority:** RESUME-PRIORITY-BRIEF P1 (best value-per-hour on the board)
**Type:** Code-only defect fix + regression test. No data migration. No new AWS resources.
**Depends on:** nothing. **Interacts with:** 1397 only superficially (see Out of Scope).

---

## Defect

The ingestion pipeline (Feature 1010) is designed so the SAME news story ingested from
Tiingo and Finnhub collapses into ONE DynamoDB item with both sources tracked in a
`sources[]` array. This merge **never fires in production**. Every shared story is
stored twice — once per source — silently defeating cross-source deduplication,
inflating item counts, and double-feeding downstream sentiment analysis via SNS.

Refuter-verified this session.

## Root Cause — timestamp serialization asymmetry

The two adapters produce `published_at` datetimes with different tz-awareness:

| Path | Code | Result |
|---|---|---|
| Tiingo | `src/lambdas/shared/adapters/tiingo.py:237-239` — `datetime.fromisoformat(item["publishedDate"].replace("Z", "+00:00"))` | **tz-AWARE** UTC (`...+00:00`) |
| Finnhub | `src/lambdas/shared/adapters/finnhub.py:227` — `datetime.fromtimestamp(item["datetime"])` | **NAIVE** (no tzinfo) |

The dedup storage key is built in `src/lambdas/ingestion/handler.py`:

- PK: `source_id = f"dedup:{dedup_key}"` (handler.py:969/1028; key generated by
  `generate_dedup_key()` in `src/lambdas/ingestion/dedup.py:59-98` from normalized
  headline + `YYYY-MM-DD` date — this part IS tz-tolerant at date granularity)
- **SK: `timestamp = article.published_at.isoformat()` (handler.py:1005)** — this part
  is NOT tz-tolerant.

For the same instant, `isoformat()` yields `2025-12-09T14:30:00+00:00` (Tiingo) vs
`2025-12-09T14:30:00` (Finnhub). `upsert_article_with_source()`
(`src/lambdas/ingestion/dedup.py:152-278`) keys its `update_item` on
`{"source_id": ..., "timestamp": ...}` (dedup.py:197). Different SK string → the
conditional update fails, the follow-up `get_item` misses, and `put_item` writes a
**second row** (dedup.py:244-259) instead of appending the second source. The merge
branch ("updated") is unreachable for cross-source pairs. 100% failure rate — not
intermittent.

### Verified fact: finnhub.py:388 is NOT on this path

`finnhub.py:388` — `date=datetime.fromtimestamp(timestamps[i])` — constructs
`OHLCCandle.date` inside `get_ohlc()` (the `/stock/candle` price endpoint). It never
feeds `published_at`, `generate_dedup_key`, or the news SK. It is a *separate* latent
naive-timestamp issue on the OHLC path and is **explicitly OUT OF SCOPE** for 1398
(changing it here would be an unverified edit to an unrelated data path). Signposted
for a future OHLC-focused feature.

### Why the naive value is "correct but unequal"

Finnhub's `datetime` field is a UNIX timestamp (seconds since the epoch). Epoch
seconds are UTC-anchored by definition. On Lambda (`TZ=UTC`) the naive
`fromtimestamp()` result has the same wall-clock digits as the true UTC time — the
strings differ only by the missing `+00:00` suffix. So the stored instant is not
wrong today; only key equality is broken. On a non-UTC host (local dev, tests), the
naive conversion additionally shifts the wall clock and can even change the
`YYYY-MM-DD` used in the dedup PK hash.

## Functional Requirements

- **FR-001 (normalize Finnhub tz):** The Finnhub news adapter MUST parse the epoch as
  tz-aware UTC: `datetime.fromtimestamp(item["datetime"], tz=UTC)` at
  `finnhub.py:227`. (`UTC` is already imported at finnhub.py:8.)
- **FR-002 (tz-invariant dedup key):** The dedup storage key (PK hash date AND SK
  string) MUST be invariant to how a source serializes its timestamp. Both adapters'
  `published_at` for the same UTC instant MUST produce byte-identical
  `isoformat()` output. Enforced by a defense-in-depth guard in
  `_process_article` (handler.py, near :1005): if `published_at.tzinfo is None`,
  treat it as UTC before building the SK — so a future adapter regression cannot
  silently resurrect this bug.
- **FR-003 (cross-source merge works):** A story with the same normalized headline
  and the same published instant, ingested from Tiingo then Finnhub (and vice
  versa), MUST result in exactly ONE item whose `sources` contains both, with per-source
  `source_attribution` populated — the `"updated"` branch of
  `upsert_article_with_source` must actually be taken.
- **FR-004 (regression test, fails-before/passes-after):** A unit test MUST construct
  `published_at` through the REAL adapter parse code (both adapters, same instant),
  run both articles through `_process_article` (or the upsert layer keyed on their
  real SK strings), and assert a single logical item / merge result. The test MUST
  FAIL on current `main` code and PASS with FR-001+FR-002 applied.

## Success Criteria

1. The FR-004 test demonstrably fails before the fix and passes after (both runs
   recorded in the PR).
2. Post-fix, ingesting the same story from both feeds produces one row, not two
   (`result == "updated"` for the second source; `sources == ["tiingo", "finnhub"]`).
3. Existing Tiingo-path behavior byte-identical: no change to any Tiingo-produced SK.
4. All existing ingestion unit tests still pass
   (`tests/unit/ingestion/test_cross_source_dedup.py`, `test_upsert_with_source.py`,
   `test_dedup_key_generation.py`, adapter tests).
5. `finnhub.py:388` untouched.

## Edge Cases

- **DST:** UTC has no DST; epoch→UTC-aware conversion is DST-immune. The OLD naive
  code was DST-sensitive on non-UTC hosts (wall clock shifts with local offset). The
  fix removes host-tz sensitivity entirely.
- **UTC midnight boundary:** a story published at `00:00:00Z` parsed naively on a
  host west of UTC lands on the PREVIOUS calendar date → different `YYYY-MM-DD` in
  the dedup PK hash → even the PK diverges. On Lambda (TZ=UTC) this never happened;
  after the fix it cannot happen anywhere. Test includes an exact-midnight epoch.
- **Feed already tz-aware:** Tiingo already emits `+00:00`; the FR-002 guard is a
  no-op for aware datetimes (idempotent — MUST NOT double-convert).
- **Finnhub epoch timezone:** UNIX timestamps are timezone-independent seconds since
  `1970-01-01T00:00:00Z`; Finnhub documents `datetime` as a UNIX timestamp.
  `fromtimestamp(x, tz=UTC)` is the exact decoding. No offset assumption is being
  *added* — the naive code already implicitly assumed UTC via the Lambda host tz.
- **Same story, different publish seconds across feeds:** the SK is second-granular.
  If Tiingo says `14:30:00Z` and Finnhub says `14:30:07Z` for the same story, the
  SKs still differ and the rows still won't merge even after this fix (the PK hash
  matches, but the item Key includes the SK). This is a pre-existing design
  limitation of Feature 1010, NOT part of LB-1, and is OUT OF SCOPE — signposted as
  an open question below. This fix removes the *systematic 100%* failure mode.

## Adversarial Review #1 (spec)

**Attack 1 — "Does normalizing tz change the SK for EXISTING Tiingo rows, breaking
their dedup?"** No. The Tiingo parse path is untouched and already tz-aware; every
Tiingo SK before and after the fix is byte-identical (Success Criterion 3, covered by
a task). The FR-002 guard is a no-op for aware datetimes.

**Attack 2 — "New Finnhub writes gain `+00:00`; do they stop matching OLD naive-SK
Finnhub rows?"** Correct, and accepted: during the ingestion lookback window (~7
days), a re-crawled story that already exists as an old naive-SK row will write one
new aware-SK row instead of deduping against the old one — a bounded, transient
duplication that TTL clears. Note the asymmetry: those old rows were *already*
un-mergeable with Tiingo rows; the fix does not make any currently-working merge stop
working, because cross-source merge currently works 0% of the time. Spec records
this in the plan's rollout note rather than pretending the transition is free.

**Attack 3 — "Does the fix shift any published_at displayed to users?"** The instant
is unchanged (epoch decoded as UTC either way on Lambda where TZ=UTC). The *string*
`metadata.published_at` gains a `+00:00` suffix for Finnhub items.
`NewsItem.from_dynamodb_item` uses `datetime.fromisoformat` (news_item.py:158), which
accepts offsets. A verification task greps remaining consumers of
`metadata.published_at` / the SNS `timestamp` field to confirm none do naive string
comparison or fixed-width slicing beyond `[:10]` (which is offset-safe).

**Attack 4 — "Is the Finnhub epoch actually UTC, or local/exchange time?"** UNIX
timestamps are timezone-independent by definition; Finnhub's docs call the field a
UNIX timestamp. The current code already treats it as UTC implicitly (Lambda TZ=UTC)
and stored values have been correct instants — only the serialization differed. If
Finnhub were secretly sending exchange-local wall-clock encoded as epoch, the OLD
code would have been equally wrong; the fix changes nothing about that risk, and the
stored instants observed in preprod match Tiingo's for shared stories (that is
precisely how the refuter demonstrated the near-miss SKs).

**Attack 5 — "The test could be vacuous: hand-built datetimes would pass before the
fix."** FR-004 explicitly requires `published_at` to flow through the real adapter
parse lines (mocked HTTP payloads, real parse code). Fails-before evidence is a
required, recorded gate.

**Verdict:** Spec is sound. Root cause is cited to exact lines, :388 scope-creep trap
is explicitly defused, transition cost (Attack 2) is acknowledged rather than hidden.
